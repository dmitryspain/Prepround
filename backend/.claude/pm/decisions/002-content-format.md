# 002 · Контент: YAML у репо, застосунок читає з бази

- **Статус:** accepted (2026-11-13)
- **Хто вирішив:** власник («додавати питання будемо самі», варіанти відповіді, гнучкі рівні). Формат файлів запропонувала головна сесія.

## Контекст

Питання пише лише власник, часто пачками і з допомогою AI, з подальшою вичиткою. Згодом їх можуть бути десятки тисяч. Власник питав, чи не буде ідіотизмом тримати 100 000 питань у файлах.

## Рішення

1. **Файли — це джерело контенту, а база — те, з чим працює застосунок.** API ніколи не читає YAML. `Prepround.ContentTool import` кладе контент у PostgreSQL.
2. **Один файл на тему**, а не на питання.
3. **Розмір:** одне питання з поясненням займає ≈ 1 КБ (кирилиця в UTF-8 — 2 байти на літеру). 100 000 питань ≈ 100 МБ тексту, у git після стиснення ≈ 25–35 МБ. Файл теми на 300 питань ≈ 300 КБ, а GitHub обмежує файл 100 МБ. Якщо тема виросте понад ~1000 питань, PM пропонує розбити її на кілька файлів.
4. **Коли переходити на адмінку:** коли з'являться автори без git або треба буде правити питання без деплою. Тоді джерелом стане база, а git — архівом. Id стабільні, тому перехід зводиться до одного імпорту.

## Формат

```
content/
  it/
    field.yaml          # галузь: шкала рівнів, напрями, стеки
    topics/
      ef-core.yaml      # тема + її питання
      sql.yaml
```

`field.yaml`:

```yaml
id: it
title: IT
levels:                 # порядок = ранг, від нижчого до вищого
  - id: junior
    title: Junior
  - id: middle
    title: Middle
  - id: senior
    title: Senior
directions:
  - id: backend
    title: Backend
    stacks:
      - id: dotnet
        title: .NET (C#)
        topics: [csharp, dotnet-clr, dotnet-async, aspnet-core, ef-core, sql, architecture, messaging, azure, docker-k8s]
```

`topics/ef-core.yaml`:

```yaml
id: ef-core
title: Entity Framework Core
description: DbContext, відстеження змін, міграції, завантаження зв'язків, N+1, продуктивність.
questions:
  - id: ef-core-001
    level: middle
    type: single              # single | multiple
    text: Що робить `AsNoTracking()` в EF Core?
    options:
      - text: Вимикає відстеження змін для отриманих сутностей
        correct: true
      - text: Кешує результат запиту між викликами
      - text: Автоматично завантажує пов'язані сутності
      - text: Робить запит асинхронним
    explanation: >
      Сутності не потрапляють у ChangeTracker, тож читання швидше і займає менше пам'яті.
      Але зміни в них SaveChanges не збереже, поки їх не приєднати через Attach або Update.
  - id: ef-core-002
    level: senior
    type: multiple
    text: Які з цих запитів спричинять проблему N+1?
    code:                      # необов'язково
      lang: csharp
      source: |
        var orders = await db.Orders.ToListAsync();
        foreach (var o in orders) Console.WriteLine(o.Customer.Name);
    options:
      - text: …
        correct: true
      - text: …
        correct: true
      - text: …
    explanation: …
```

- **Inline-код** у `text`, в `options[].text` і в `explanation` пишемо в бектиках. Блок коду кладемо в `code`. Markdown не підтримуємо: менше ризиків XSS і менше залежностей.
- **Мова:** базова — українська, переклад — ключі `<ключ>_en` поруч з оригіналом (рішення 006, розділ «Уточнення: переклади» нижче).

## Правила валідації (`ContentTool validate`; `import` спершу виконує ті самі перевірки)

Помилка в будь-якому правилі дає exit 1 і список «файл: id: що не так». Імпорт за помилок нічого не змінює.

1. Усі id (галузі, рівня, напряму, стеку, теми, питання) — kebab-case `^[a-z0-9]+(-[a-z0-9]+)*$`.
2. Id рівнів, напрямів і стеків унікальні в межах галузі. Id тем унікальні в межах галузі, а id питань — у всьому контенті.
3. Ім'я файлу теми дорівнює її `id`, а назва папки галузі дорівнює `id` у її `field.yaml`. Теми однієї галузі лежать у `<галузь>/topics/`.
4. Кожен id теми в `stacks[].topics` існує в `topics/`, без дублікатів у межах стеку.
5. `level` питання — це id з шкали його галузі.
6. `type` має значення `single` або `multiple`. `single` має рівно 1 правильний варіант, `multiple` — щонайменше 2 правильних і щонайменше 1 неправильний.
7. Варіантів 2–8. Тексти варіантів непорожні й неповторювані в межах питання.
8. `text` і `explanation` непорожні. Якщо є `code`, то `code.source` непорожній, а `code.lang` відповідає kebab-case.
9. Невідомі ключі YAML — це помилка, а не тиша: так ловимо друкарські помилки на зразок `corect: true`.
10. `sources` у питанні **необов'язкове** (рішення 004). Якщо ключ є — непорожній список абсолютних `https`-URL без пробілів і повторів. Поле живе лише в YAML: `import`, БД і API його не бачать.

## Семантика імпорту

- Імпорт ідемпотентний: повторний запуск без змін у файлах не змінює даних.
- Upsert іде за id. Сутність, якої більше немає у файлах, отримує `IsActive = false`. Нічого не видаляємо, бо клієнти зберігають id у своїй історії.
- Рівні зберігаються з рангом (позиція в шкалі, починаючи з 1), стеки — з порядком тем.
- Імпорт проходить в одній транзакції.

## Уточнення реалізації (PM, 2026-11-14)

Не змінюють рішення, а фіксують поведінку, прийняту під час PRP-003 і PRP-014, щоб наступні картки на неї спирались.

- **Читач і валідатор розділені.** Читач (`YamlContentReader`, Infrastructure) відповідає за синтаксис, правило 9 і форму значень; `ContentValidator` (Application) — за правила 1–8 і 10. Якщо читач знайшов помилки, правила 1–8 і 10 у цьому прогоні не запускаються: інакше один зламаний файл теми дає хибні «Теми X немає» в кожному стеку. Ціна — автор може побачити помилки за два прогони.
- **Один крок «прочитати й перевірити»** живе в Application за інтерфейсом `IContentReader` (PRP-014). Ним користуються і `validate`, і `import` (PRP-004), тож їхні перевірки не можуть розійтись.
- **Принцип правила 9 поширюється на файли** (PRP-014): будь-який `.yaml` / `.yml` (у будь-якому регістрі) у дереві контенту, який читач не читає, — помилка. Читаються лише `<галузь>/field.yaml` і `<галузь>/topics/*.yaml`. Файли й теки з `.` на початку та файли не-YAML пропускаються.
- **Порожній корінь** (жодної теки галузі) і **тека галузі без `field.yaml`** — помилки: найчастіше це неправильний шлях, а імпорт такого вмісту деактивував би весь каталог.
- Порожній `title` галузі, рівня, напряму, стеку чи теми — помилка; `description` необов'язковий. `correct` приймає лише `true` / `false`. Унікальність id з правила 2 перевіряється окремо для рівнів, напрямів і стеків.
- Синтаксичні помилки містять англійську деталь від YamlDotNet після українського речення. Прийнято.
- **Відомі діри, свідомо відкладені:** порожні `levels`, `directions`, `stacks` чи `topics` стеку не є помилкою (беклог, «Ідеї»: картка перед першою новою галуззю).
- **Порядок варіантів у файлі** нічого не означає для користувача: сервер перемішує варіанти (spec 5.2, критерій у PRP-006). У seed правильні варіанти стоять першими, і це безпечно лише завдяки перемішуванню.

## Уточнення: чернетки тем (PM, 2026-11-19, рішення 005, розділ 6; реалізує PRP-023)

- **Поле теми `draft`** (`true` / `false`, необов'язкове, за замовчуванням `false`) стоїть на верхньому рівні файлу теми поруч з `id`, `title`, `description`. Небулеве значення дає помилку читача.
- **`validate`** перевіряє чернетки за тими ж правилами, що й інші теми.
- **`import <тека>`** за замовчуванням не бере питань тем-чернеток. Такі питання вважаються відсутніми у файлах: нових не додає, раніше імпортовані позначає `IsActive = false` (див. «Семантика імпорту»). Саму тему (назву, опис, місце в стеках) імпортує як завжди.
- **`import <тека> --include-drafts`** імпортує все. Ним користуються лише dev-БД і хвилі контенту.
- **Звідки береться прапорець.** Нова тема з'являється чернеткою. Знімає `draft` лише головна сесія після PASS фактчеку теми.
- **Аварійне вимкнення опублікованої теми:** знову `draft: true`, потім `import` у прод.
- **БД, API і spec 5 про `draft` нічого не знають.** API, як і раніше, віддає лише активні питання.

## Уточнення: переклади (PM, 2026-11-19, рішення 006; реалізують PRP-025, PRP-026, PRP-031)

- **Базова мова — українська:** обов'язкова й повна. Мови перекладу перелічені в одній константі `ContentLanguages` (`Prepround.Application`), зараз лише `en`.
- **Ключі перекладу мовою L** стоять одразу після базового ключа:
  - `title_L` — у галузі, рівні, напрямі, стеку й темі;
  - `description_L` — у темі;
  - `text_L` і `explanation_L` — у питанні;
  - `text_L` — у варіанті;
  - `draft_L` — булеве, у темі.

  Інші суфікси й регістри (`text_de`, `title_EN`, `code.source_en`) — невідомий ключ, правило 9.
- **Спільне для мов:** id, `level`, `type`, `correct`, порядок варіантів, `code` (коментарі в коді англійською), `sources`.
- **Правило 11 (PRP-025):**
  - значення перекладу непорожнє;
  - питання мовою L має або всі ключі `text_L`, `explanation_L` і `text_L` кожного варіанта, або жодного;
  - тексти варіантів мовою L не повторюються в межах питання.
- **Правило 12 (PRP-031, після хвиль перекладу):** тема без `draft: true` і без `draft_L: true` має `title_L`, `description_L` (якщо `description` непорожній) і повний переклад мовою L кожного питання.
- **`import`:**
  - назви кладе в jsonb-словники сутностей, а переклади питань — у `QuestionTranslations`;
  - зниклий переклад видаляє: у перекладів немає id, які тримають клієнти;
  - без `--include-drafts` не бере перекладів питань мовою L тем із `draft_L: true`, а питання тем із `draft: true` не бере зовсім.

  Підсумок має рядок `Переклади питань: додано, оновлено, видалено`. `Питання: …` від перекладів не залежить.
